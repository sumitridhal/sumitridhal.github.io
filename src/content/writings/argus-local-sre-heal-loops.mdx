Most SRE agent demos start with a pitch deck and end with a managed cloud service. I wanted the opposite: a control plane that runs on my laptop, where I can watch every step and kill the loop if the agent does something I would not have done.

## The shape

Argus is a local meta-agent SRE control plane. The core loop is simple:

1. **Scaffold** an agent from a Hono template
2. **Inject** a failure — bad env, broken route, memory leak
3. **Open an incident** automatically when health checks fail
4. **Run SRE** — the agent reads logs, proposes a fix, writes a diff
5. **Approve** only if tests are green and the diff is non-empty
6. **Merge and redeploy** on the local branch

That last step is the one most demos skip. Argus does not push to GitHub. The heal loop stays local: branch, diff, approve, merge, redeploy. HITL git without the remote gate.

## Why local matters

Cloud SRE platforms are useful when you have a fleet. When you have one service you are building and testing, a cloud control plane is overhead. I want to see the logs in my terminal, review the diff in my editor, and say yes or no before anything changes.

The concurrency constraint is intentional: one incident at a time. If the agent opens an incident and proposes a fix, nothing else runs until that loop closes. Serialized execution is a feature when you are learning what the agent actually does under pressure.

## What I learned

The approval gate is the entire product. Without it, you have a script that edits code and restarts services — interesting for a demo, dangerous for anything you care about. With it, you have a feedback loop where the human stays in the decision seat and the agent stays in the execution seat.

The second thing I learned is that injecting failures is more useful for testing the agent than for testing the service. I already know my service breaks when the database goes down. What I did not know is whether the agent would try to restart the database, patch the connection string, or add a retry loop. Each of those is a different kind of fix, and which one the agent picks tells you whether your prompts are any good.

## The stack

Next.js for the dashboard, a Node supervisor for health checks and incident lifecycle, Docker for the target service, Claude CLI for the agent, SQLite for state, and OpenTelemetry for the observability layer. Everything runs locally. No API keys required beyond the LLM provider.

## Where it goes

Phase 1 is one agent, one service. That is the proof. Multi-agent fleets and remote deployments are interesting problems, but they are not the first problem. The first problem is: can an agent propose a fix, can a human review it, and can the system close the loop without anyone SSHing into a box?

For my use case, the answer is yes. The rough edges are in the prompts, not the plumbing.
