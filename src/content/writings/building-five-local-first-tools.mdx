Over the past few months I shipped five tools. Each one runs locally, stores data on disk, and solves a specific problem:

- **Argus** — SRE control plane for agent heal loops. Inject a failure, watch the agent propose a fix, approve or reject the diff.
- **Synvix** — Freewrite studio that drafts in my voice using a corpus of my past writing.
- **Motion Forge** — Video and stills workspace with shader effects, multi-layer compositor, and local FFmpeg export.
- **Signal** — Morning command center that aggregates technical feeds, triages by relevance, and produces a daily digest.
- **Talos** — SDLC command center and factory kernel for orchestrating agent-driven development workflows.

None of them share a backend. None of them require a login. None of them call a server I do not control, except for LLM inference.

## Why five tools and not a platform

The honest answer is that I built them in order, and each one solved a real problem I was having that week. Argus came from wanting to test agent reliability. Synvix came from wanting to write LinkedIn posts that did not sound like ChatGPT. Motion Forge came from needing shader stills for this site. Signal came from wasting mornings on tab-surfing. Talos came from wanting to orchestrate the other four.

The principled answer is that small, single-purpose tools compose better than monoliths. I can run Argus and Signal at the same time without them knowing about each other. I can use Motion Forge to generate a cover image and Synvix to write the caption. They share a filesystem, not a database.

## The local-first pattern

Every tool follows the same shape:

1. **Next.js** for the UI
2. **SQLite** or flat files for state
3. **Claude CLI** or API for LLM work
4. **No auth, no cloud sync, no user accounts**

This is not a philosophical commitment to local-first computing. It is a practical observation: for tools that one person uses, local-first is the fastest path from idea to working software. No auth flow to build, no database migrations to manage, no billing to implement, no GDPR to worry about. The tradeoff is that nobody else can use them without cloning the repo and running `npm install`. For now, that is fine.

## What transfers

The patterns that showed up in all five projects:

**Approval gates matter more than automation.** Argus taught me that the value of an agent is not that it can fix things automatically. It is that it can propose fixes for a human to review. The gate is the product.

**Corpus beats configuration.** Synvix taught me that feeding the model examples of what you want is more effective than describing what you want. Show, do not tell, applies to prompts too.

**Export is the feature.** Motion Forge taught me that a creative tool without export is a toy. The shader playground is fun; the FFmpeg pipeline is useful.

**Triage beats consumption.** Signal taught me that reading less is more valuable than reading faster. The triage view is the core interaction; everything else is enrichment.

**Orchestration is a separate tool.** Talos taught me that trying to build orchestration into each tool makes each tool worse. Pull it out, make it its own thing, and let the tools stay simple.

## What is next

Publishing. The tools exist, the portfolio site shows them, but the content pipeline — turning project work into posts, threads, and demos — has been manual and inconsistent. That is the gap I am closing now.

The five tools are the work. The writing is the proof that the work exists. Both matter if you are building in public as a solo engineer.
