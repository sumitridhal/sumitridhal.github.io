I wrote this for the moment where a WebGL habit stops helping. In WebGL, a small fullscreen sketch can survive on muscle memory: bind a buffer, set a uniform, draw. In WebGPU, the same sketch asks you to name the queue, the bind group layout, the pipeline, and the resource lifetime before a pixel moves. That feels like ceremony until you realize the ceremony is the API telling you where the cost lives.

WebGPU asks you to think in explicit queues, bind groups, and pipelines instead of the implicit state machine many of us grew up with in immediate-mode GL. That verbosity is the contract: the driver gets a smaller decision surface, which tends to mean more predictable performance on integrated GPUs and laptops.

```wgsl
@group(0) @binding(0) var<uniform> params: Params;

@vertex
fn vsMain(@builtin(vertex_index) vi: u32) -> @builtin(position) vec4f {
  let pos = array<vec2f, 3>(vec2f(-1.0, -1.0), vec2f(3.0, -1.0), vec2f(-1.0, 3.0));
  return vec4f(pos[vi], 0.0, 1.0);
}
```

The live block here is still a WebGL2 stand-in because it needs to run everywhere this site runs. That mismatch is a useful reminder: the visual idea is not the hard part. The hard part in WebGPU is making resource ownership explicit enough that a future compute pass, texture upload, or post stack does not turn into guesswork.

A tiny ergonomic layer on top—typed shader nodes, macro helpers, or a scene graph that emits pipelines—can buy readability without hiding the two things that still matter: how often you switch pipelines and how wide your memory barriers are. Abstractions that obscure those two knobs eventually show up as jank.

Reach for WebGPU when you need compute shaders beside graphics, large structured buffers, or tighter control over multi-pass rendering. Stay on WebGL when your asset is stable, your audience still includes older Safari constraints, or the port cost outweighs a single fullscreen effect. The honest test is not whether WebGPU is newer; it is whether explicit control removes more uncertainty than it adds.
