A **bento layout** names the pattern: one viewport, many rounded tiles of different sizes, separated by consistent gutters. Product dashboards, mobile home screens, and editorial landing pages all use it when each card carries one nugget—a count, a meeting, a hero phrase—instead of a long scroll of uniform rows.

The visual polish—gradients, glass, serif headlines—gets attention first. The part that keeps the layout maintainable is simpler: **a grid with explicit spans**.

## Grid as the contract

Pick a column count and stick to it. On a phone-width canvas, **four columns** is a practical default: you can build 1×1 squares, 2×1 wide strips, 1×2 tall strips, and a 2×2 hero without leaving holes.

```css
.bento {
  display: grid;
  grid-template-columns: repeat(4, minmax(0, 1fr));
  gap: 0.75rem;
  grid-auto-rows: minmax(4rem, auto);
}
```

Each tile is a grid item. Size comes from **`grid-column`** and **`grid-row` spans**, not from `position: absolute` or hand-tuned `width` percentages:

```css
.bento__tile--stat {
  grid-column: 1;
  grid-row: 1;
}

.bento__tile--wide {
  grid-column: 2 / span 3;
  grid-row: 1;
}

.bento__tile--hero {
  grid-column: 1 / span 2;
  grid-row: 2 / span 2;
}
```

Three details that prevent “mystery overflow” on real content:

- **`minmax(0, 1fr)`** on columns lets text truncate inside tiles instead of forcing the grid wider than the viewport.
- **`grid-auto-rows: minmax(…, auto)`** gives short tiles a floor height while letting copy grow tall tiles naturally.
- **`gap`** is your single spacing knob—match it to **`border-radius`** so gutters and corners feel like one system.

Markup stays boring on purpose:

```html
<div class="bento">
  <article class="bento__tile bento__tile--stat">…</article>
  <article class="bento__tile bento__tile--wide">…</article>
  <article class="bento__tile bento__tile--hero">…</article>
</div>
```

## Sizing rules that keep the grid honest

**Prefer spans over absolute positioning.** Absolute tiles look fine in a Figma mock; in production they drift when font size, locale, or dynamic type changes. Grid spans reflow with the same column math at every breakpoint.

**One hero anchor.** A single 2×2 (or full-width) tile establishes hierarchy. A second tile competing at the same scale reads as noise unless you widen the grid or split the screen into sections.

**Square vs text tiles.** Use **`aspect-ratio: 1`** on icon or numeric tiles so 1×1 cells stay square. Text-heavy tiles should use **`min-height`** (or extra row span) instead of forcing a ratio that fights wrapping.

**Responsive collapse.** Below a breakpoint, drop to **two columns** and remap spans: a `grid-column: span 3` wide tile becomes `span 2`; a 2×2 hero may become full width (`span 2`) with a shorter row span. Keep the same class names and change span values in a media query rather than duplicating markup.

## Styling layer (light touch)

Layout and surface are separate concerns. Once spans are stable:

- **Radius + shadow** — large `border-radius` (roughly 16–24px at mobile scale) and a soft, low-opacity shadow separate tiles without heavy borders.
- **Surface variants** — white cards for dense copy; **`linear-gradient`** for hero tiles; **`backdrop-filter: blur()`** with semi-transparent fills for glass overlays on busy backgrounds. These are CSS modifiers (`data-variant="glass"`), not new layout rules.
- **Type pairing** — a high-contrast **serif** for big numbers and hero words; a **sans** for labels, pills, and metadata. You do not need a full type scale on day one—two roles are enough.

## When to use it—and a simpler variant in this repo

Bento works when users scan **many small facts** at once: tasks due today, balance summaries, team avatars, one promotional hero. Reach for a flat list or a single column when every item needs paragraphs of explanation.

This site already ships a minimal 2×2 bento in the [home work picker](/#work)—`DeckBentoCenter` uses the same grid idea with one full-width tile and two half-width rows. The preview in this note stretches that idea to asymmetric spans; the mechanics are identical, only the span map grows.

If you adopt the pattern, sketch the span map on paper first (which tile is 1×1, 2×1, 2×2), then code modifiers. Polish gradients last—they hide bad placement for a demo and expose it in production.
